Desire coding

Desire coding is when end users build software for their unmet needs with AI assistance, like the worn desire paths that cut across a lawn where paved routes do not reach.

Just as landscape planners read desire paths to decide where to pave, organizations should read desire-coded tools to decide which of those needs to meet at scale.

The vibe leaves a trail

Vibe coding, as Andrej Karpathy first described it, is a way of working in which the builder gives in to the vibes and forgets “that the code even exists.” The term describes how someone builds software, while leaving open what the software is for. Desire coding focuses on the unmet need that led them to build it.

When someone makes a tool because no software meets their need, or the software they have works poorly, the tool shows where the existing systems fall short. Like a path worn across a lawn, it shows where people needed to go and found their own way.

What organizations can learn

Some planners read desire paths before deciding where to pour concrete. Organizations can learn from the tools people build for themselves in much the same way. Each tool is a demand signal, showing what someone needed to do, how they chose to do it, and which parts of the existing system they worked around or gave up on. Those choices can help leaders decide which needs to meet at scale.

The tool itself still needs scrutiny. A security audit revised in September 2026 found at least one vulnerability in 91 percent of 200 publicly deployed vibe-coded apps. That finding gives organizations a reason to review desire-coded tools before anyone beyond their makers relies on them.

Nic Lydon made a similar comparison in May 2026. He described vibe-coded workplace tools as desire paths and called on security and engineering teams to provide a governed platform where employees could keep building.

Where Lydon’s paved path is a platform for building, the term desire coding puts the emphasis on paving the need itself, so the work starts with understanding the need behind each tool. What the tool does, the data it holds, and the workflow it replaces all help explain why someone built it. With that understanding, an organization can decide whether to pave the path by meeting the need through shared systems, reroute people to a tool that already meets it, or fence the path off.

Where the idea comes from

The metaphor has a history in software design. In a 1998 Dr. Dobb’s Journal interview, Larry Wall compared Perl to the sidewalks UC Irvine reportedly built along trails people had worn across its lawns. The W3C’s 2007 HTML Design Principles advised the language’s designers to consider adopting practices already common among web authors, under the principle “Pave the Cowpaths.” On the working group’s mailing list that August, Lachlan Hunt compared the principle to desire lines.

In management, the image can carry a different meaning. In 1990, Michael Hammer told Harvard Business Review readers that “it is time to stop paving the cow paths,” warning against automating outdated processes that needed redesign. A desire path shows where people have already found a way around such a process. Reading it can help an organization see what needs to change.

The connection also appears in information systems research. In 2024, Manuel Wiesche, Nina Böhm, and Michael Schermann described computer workarounds as digital desire paths that can help designers improve a system. Desire coding names that idea for a setting where people can use AI to build the software they need themselves.
